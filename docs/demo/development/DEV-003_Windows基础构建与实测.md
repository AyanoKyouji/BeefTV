## 1. 输入与资源

读取 DEV-001/002 报告、真实仓库构建说明、适用规范及 T504。用户回传报告已记录 Windows 11 专业版 10.0.26300 / AMD64、Go 1.27.3、Bun 1.4.2、Node 24.15.0、UCRT64 GCC/binutils 和 WebView2，原生构建退出 0、独立窗口启动可用。当前会话只核对报告，未建立 Windows 操作通道。报告第 7/8 节的宿主就绪、项目操作及退出恢复仍待执行；按用户要求安排在后续 Windows 阶段回归，Mac 日常开发继续。

目标为 Windows x64。先核实实际电脑是否满足目标，再使用；若不符则记录阻塞，不将其他架构运行冒充 x64 验证。实际构建入口、宿主或 CI 可用性按真实项目确定，不预先保证可跨平台构建。

## 2. 允许与禁止范围

允许复用现有 Windows 打包入口，准备必要依赖、生成完整运行产物、核查随包资源并在现有 Windows 电脑测试；局部修复阻碍打包或运行的必要脚本、配置、资源路径和启动接线。

不替换 Wails、不引入另一套发行体系、不进行正式商业发布、不用 Vite 开发页面冒充客户端、不要求靠另开 Node/Go 开发服务器才可运行。Node Agent 及必要资源按现有发行机制提供，系统运行前提单独说明。

现有 Windows 电脑可直接实测，无需先创建虚拟机。无法从当前会话直接操作该电脑时，提供本任务第 4 节及实际产物位置，由用户执行；准确记录是谁、在哪台设备上操作，不宣称已获得远程控制能力。

## 3. 构建步骤

1. 记录当前分支/Commit、工作区差异和 DEV-002 结果；确认没有覆盖已有工作。
2. 查阅并按实际构建脚本处理前端产物、Go 业务组件、Node Agent Runtime、必要媒体/资源和系统运行依赖；以实际发行方式为准，不机械要求不存在的独立 Go 运行程序。
3. 执行 Windows x64 完整构建，记录命令、环境、输出、产物路径和可核查标识（如文件校验值）。失败先定位真实依赖或脚本问题，必要局部修复后验证。
4. 将同一标识产物和必要测试资料提供给实际 Windows 环境，记录传递方式。不要把开发机的缓存、凭证和完整工作区当作随包运行依赖。
5. 按下表执行实测并留存证据。仅构建成功或产物已传送，不能关闭任务。

Windows 尚未操作则该部分 NOT TESTED，任务 Blocked 或继续进行；启动实际失败记录 Failed，保留原因。构建成功和设备实测分开报告。确认已有机制满足可为 Verified；必要修复并验证通过可为 Fixed。
