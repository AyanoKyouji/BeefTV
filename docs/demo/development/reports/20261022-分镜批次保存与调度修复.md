# 分镜批次保存与调度修复

## 现象与证据

用户从分镜节点提交未完成分镜图，出现三个图片节点；手动生成第一张时被保存屏障阻止，尚未发起模型请求。

原生界面同时存在「画布已在别处更新」和「已保存在本地」。只读检查工作区数据库确认后端文档尚无这三个图片节点，原脚本的结构化行仍为空白行；文本任务的真实分镜 JSON 已写入节点正文。界面上的已解析分镜和新增图片属于尚未确认的本地编辑，不能直接加载旧数据库文档覆盖。

## 修复

1. 刷新合并先结算同一任务的生成状态，避免把界面的 loading/error 展示状态与后台已绑定成功结果判为人工编辑冲突。真实内容冲突、不同任务、删除与账号切换保护保留。
2. 移除本机模式下直接跳过批次调度的分支；任务仍使用现有后端任务接口、并发限制与生成执行器。
3. 批次调用现有画布完整保存屏障，等待节点、连线、分镜行关联等保存确认后才查询额度和提交。保存失败时将尚未提交的等待项记为可重试失败，保留原因，避免无限等待和收费请求。
4. 保存等待结束后重读当前批次；取消、节点变化、页面生命周期结束或账号切换不沿用旧快照提交。
5. 本机顶栏与保存详情尊重冲突、失败和保存中状态，不再一律显示绿色「已保存在本地」。

## 验证

- 新增回归用例先在原实现复现同任务分镜刷新冲突，修复后通过。
- 分镜刷新/文档合并 26 项、保存屏障 12 项、刷新接缝 8 项、真实编辑冲突 2 项、提交日记及恢复 69 项、本机批次保存门槛 4 项，共 121 项针对性测试通过。
- TypeScript 检查通过。
- 调度测试使用模拟任务接口，覆盖保存等待、保存失败零提交、保存期间取消、账号切换及并发额度。
- 本地发布门禁、前端与 Wails 构建、签名及内置媒体运行时检查通过，已原位更新唯一的 YUNTV 应用。
- 更新后重新打开原画布，未选择加载旧文档覆盖草稿。原分镜、三个图片节点和三条关联连线恢复并保存到 SQLite；后端版本从 33 推进到 34，三个分镜行都有实际描述、视频提示词和图片绑定。
- 原生界面不再显示外部版本冲突，「生成未完成分镜图」入口已可用。原第一镜的失败提示保留为历史，另外两项为已停止；需要用户重新提交未完成图片。
- 对比更新前数据库备份与更新后数据库，10 个任务的身份和状态完全一致，没有新增模型任务。

更新前备份了此应用的草稿缓存和一致性数据库副本，位于 Git 忽略的 `.local/storyboard-save-20261022/`。两项尚未提交的图片任务通过原生界面停止；原分镜和三个图片节点保留。未重试任何真实图片或视频生成。

原生验证截图为同目录下的 `native-saved-retry-ready.png`。上述验证确认保存、恢复和提交门槛；本次没有验证真实 Flux 生成结果。
